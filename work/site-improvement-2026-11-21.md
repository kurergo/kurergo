# KurerGO: доработка дизайна и сценария регистрации

Работа по `KURERGO_SITE_IMPROVEMENT_PLAN.md`. Начало: 21 ноября 2026 г.; финальная проверка: 22 ноября 2026 г.

## Что мешало регистрации

- Сразу за первым экраном шёл длинный информационный блок; затем несколько похожих секций. Выбор формата и шаги подключения находились далеко от основного предложения.
- Калькулятор конкурировал с регистрацией. Он показывал условные начисления до расходов, хотя подзаголовок обещал расчёт после расходов.
- Карточки форматов не давали понятного следующего действия.
- Подбор формата запрашивал контакт. При пустом webhook посетитель видел техническое сообщение о настройке CMS/n8n.
- Использовались разрозненные цели кликов, а отдельной дедуплицированной цели не было.
- Партнёрский статус объяснялся в основном внизу страницы.

## Реализовано

### Главная и общий дизайн

Светлый фон, тёмно-зелёные акценты, контрастная жёлтая основная кнопка, более короткие тексты и чёткая иерархия. На первом экране — конкретное предложение и переход к официальной регистрации. Вторичные действия ведут к форматам и помощи для уже зарегистрированных пользователей.

Карточки пешей, вело- и автодоставки содержат раскрывающиеся пояснения и ссылки на существующие инструкции. Следом показаны три шага подключения. На мобильном экране закреплён переход к регистрации с учётом safe area. Уведомление об аналитике находится в потоке документа и не перекрывает кнопки.

WIKI, городские страницы, прежние SEO-адреса и редакционный текст главной сохранены. Длинный текст главной помещён в нативный раскрывающийся блок. Калькулятор находится ниже основных сценариев; в нём отдельно показаны условные начисления и остаток после введённых расходов и процента налога. Пример явно не является тарифом или прогнозом.

Изображение первого экрана использует WebP и `srcset`: 520, 800 и 1024 px. Для стандартного изображения сгенерированы версии около 34 и 63 КБ; оригинал около 70 КБ. Новые клиентские библиотеки не добавлены.

### P0: рекламный маршрут и переходы

- Создан `/lp/rabota-kurerom/`: короткое предложение, основная CTA, форматы, требования, шаги и пять FAQ. Нет калькулятора, длинной WIKI и обязательной предварительной анкеты.
- Все регистрационные кнопки шаблонов используют `layouts/partials/registration-cta.html`.
- Адрес перехода и конечная партнёрская ссылка остаются в `hugo.toml`. Код приглашения сохранён.
- `/go/yandex-courier/` сохранён. При отсутствии согласия на аналитику JS перенаправляет сразу; при согласии предусмотрен тайм-аут 1500 мс для диагностической цели. Есть ручная ссылка и meta refresh для случая без JS.
- Непроверенные `subid`, `click_id` и UTM не добавляются к партнёрскому URL. A/B-тест прямого перехода не запускался.

### P0: требования

Необязательная проверка города, формата и возрастной категории работает локально в браузере. Телефон, точная дата рождения и документы не запрашиваются. Введённый город и возраст не отправляются в события Метрики.

Подтверждённой матрицы действующих требований нет: проверка не даёт положительного решения по возрасту или городу. Для любого сценария показаны вопросы, которые необходимо уточнить в официальной анкете. Источник, дата проверки и тексты форматов вынесены в `data/eligibility.yaml` и CMS. Изменение статуса в CMS само по себе не включает автоматическое подтверждение допуска.

Без JS кнопка интерактивной проверки отключена, есть объяснение и доступные обычные ссылки регистрации. Наличие города в справочнике не означает открытый набор.

### P0: аналитика

Счётчик: `109618174`. Загружается после выбора «Разрешить», Вебвизор отключён. Выбор и отметка уникального клика хранятся в `sessionStorage` текущей вкладки. Настройки можно открыть из футера; отказ прекращает последующую отправку событий.

| Цель | Значение |
| --- | --- |
| `registration_click` | Каждое обычное нажатие регистрационной ссылки |
| `registration_click_unique` | Первое учитываемое нажатие за сеанс вкладки |
| `outbound_yandex_courier` | Диагностический этап `/go/`, не вторая конверсия клика |
| `eligibility_check_opened` | Открытие необязательной проверки |
| `eligibility_check_completed` | Показ рекомендаций; не подтверждение допуска |
| `help_opened` | Переход по размеченной ссылке помощи |
| `calculator_change` | Изменение параметров примера |

Сеанс уникального клика здесь означает жизнь вкладки до её закрытия, а не 30-минутный визит Метрики. Повторное разрешение аналитики не создаёт вторую уникальную цель в этом сеансе. При запрете `sessionStorage` дедупликация ограничена текущим документом. Переходы в новой вкладке и другие нестандартные способы открытия ссылки не следует считать надёжно измеренными физическими нажатиями.

В событиях есть URL страницы без query, регион страницы, формат, вариант и положение кнопки; время добавляется для регистрации. UTM/yclid в исходном URL доступны счётчику после разрешения аналитики, но не сохраняются отдельно сайтом и не передаются партнёру. ClientID вручную не извлекается и с кандидатами не связывается.

**Ограничение:** события не учитывают отказавшихся от аналитики и пользователей, которые сразу перешли к регистрации до выбора. Локальные тесты не подтверждают получение целей реальным кабинетом Метрики. Клик не является подтверждённой регистрацией или оплачиваемым действием.

### Помощь, документы и CMS

- `/start/`: пять сценариев после отправки анкеты, ссылки на официальные каналы и отсутствие предложения автоматически создавать дубликат.
- `/privacy/`: фактическая схема локальной проверки, аналитики и внешнего перехода.
- `/terms/`: независимый партнёрский статус и ограничения справочных материалов.
- Сбор контактов и неработающая форма консультации удалены. Сервис n8n и бот не имитируются.
- В Sveltia CMS добавлены коллекции рекламных лендингов и условий подключения. Поля неиспользуемого webhook убраны.

## Проверки

- Hugo Extended 0.162.1, совпадает с версией workflow: сборка проходит. Результат — 171 страница, 112 aliases, два обработанных изображения.
- `node --test scripts/test-conversion.mjs`: 6 тестов. Проверены согласие/отказ, дедупликация между страницами, повторное согласие, недоступное хранилище, неизвестные условия и расчёт расходов.
- `python3 scripts/check-built-site.py <build-dir>`: сохранены все 277 прежних HTML-путей, отслеживаемых Git в `public/`. Проверены семь ключевых маршрутов, внутренние ссылки, центральные CTA, JSON-LD, canonical, sitemap и партнёрский URL.
- `git diff --check`: без ошибок.
- В браузере проверены 320×568, 390×844, 430×932 и настольный экран 1440×1000. На проверенных мобильных ширинах нет горизонтального переполнения; основная кнопка первого экрана не закрыта закреплённой панелью. На 320×568 нижняя граница CTA главной — около 439 px, лендинга — около 464 px; закреплённая панель начинается с 491 px.
- Проверка неизвестного города, категории до 18 лет и авто показывает необходимость официальной проверки. Калькулятор при начислениях 41 800 ₽, расходах 3 000 ₽ и введённых 4% показывает 37 128 ₽.
- Исходная партнёрская ссылка дала HTTP 200 при сетевой проверке. Встроенный браузер не загрузил внешнюю анкету (`ERR_CONNECTION_CLOSED`), поэтому её полный мобильный сценарий и партнёрское зачисление не подтверждены.
- Реальные iOS/Android, отключение JS в браузере, медленное соединение и полевые Core Web Vitals не измерялись. Наличие fallback без JS проверено по собранному HTML; это не заменяет ручной прогон на устройствах.

## Что остаётся до рекламного запуска

1. Сверить сохранённую партнёрскую ссылку и код с действующим кабинетом; проверить правила рекламы, бренда и допустимого сопровождения из оферты.
2. Получить подтверждённый справочник возраста, городов, документов и форматов с датами и официальными источниками. Затем отдельно реализовать решения по этой матрице; сейчас включён честный fallback.
3. В Метрике создать/проверить перечисленные JavaScript-цели и увидеть тестовый визит с входящими UTM/yclid. Согласовать замену прежней цели `registration_cta_click`, если она используется в отчётах или рекламных стратегиях. Не считать диагностическую цель `/go/` второй основной конверсией.
4. Согласовать юридические реквизиты владельца ресурса и контактный канал. Тексты описывают техническую реализацию, но не заменяют документы оператора с его фактическими данными.
5. Проверить production-деплой на GitHub Pages, реальные мобильные устройства и Core Web Vitals. После публикации настроить сравнение конверсии на сопоставимом трафике.
6. Дополнительные лендинги по намерению, бот/n8n, реестр кандидатов, постбэки и финансовый отчёт внедрять на следующих этапах по зависимостям исходного плана. Без возвращаемого партнёром ID сквозная атрибуция не заявляется.

## Публикация и откат

Изменения подготовлены в исходниках и проверены локально. По запросу владельца публикация выполняется отправкой проверенного коммита в `main` и существующим workflow GitHub Pages. Фактический результат подтверждается статусом этого workflow и проверкой production-страниц. Изменение рекламных кабинетов, запуск или пополнение рекламы не входят в публикацию. `public/` вручную не перезаписывается.

Для проверки: `hugo --minify --destination /tmp/kurergo-check`, затем `python3 scripts/check-built-site.py /tmp/kurergo-check`. GitHub Pages использует существующий workflow `.github/workflows/hugo.yml`. Для отката опубликованного изменения — обратный коммит соответствующего набора изменений с повторным деплоем через тот же workflow; исходные URL менять не требуется.

Изменения убирают выявленные UX-препятствия. Фактический рост конверсии и оплачиваемых результатов может быть установлен только после публикации и накопления сопоставимых данных.
