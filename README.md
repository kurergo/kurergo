# Курьерский сайт на Hugo

Современный лендинг для привлечения курьеров в Яндекс Еду с SEO-блогом и готовым деплоем на GitHub Pages.

## Где менять ссылки регистрации

Партнёрская ссылка и цели Метрики заданы в `hugo.toml`:

```toml
[params]
  referral_url = "https://reg.eda.yandex.ru/..."
  registration_click_goal = "registration_cta_click"
  registration_goal = "outbound_yandex_courier"
```

Все кнопки регистрации используют `layouts/partials/registration-cta.html` и открывают `referral_url` напрямую в текущей вкладке. Партнёрский код и адрес анкеты задаются только в `hugo.toml`.

`registration_cta_click` — каждое нажатие, `registration_click_unique` — первое нажатие за сеанс вкладки (`sessionStorage`, до закрытия вкладки). При заблокированном хранилище дедупликация работает до перезагрузки страницы. Адрес `/go/yandex-courier/` остался доступен для старых ссылок и отправляет диагностическую цель `outbound_yandex_courier`.

Метрика автоматически загружается при открытии страницы без дополнительного подтверждения; запись Вебвизора отключена. Баннер и кнопки выбора аналитики удалены. Описание обработки данных находится на `/privacy/`. Параметры источника остаются в исходном URL визита; сайт не дописывает рекламные идентификаторы в партнёрскую ссылку и не сохраняет их отдельно в браузере. Клик не равен регистрации или оплачиваемому действию.

## Дизайн и рекламный сценарий

- `/` — обновлённая главная; SEO-контент и городские ссылки сохранены.
- `/lp/rabota-kurerom/` — короткий рекламный лендинг без калькулятора и обязательных форм.
- `/start/` — справочная помощь после регистрации.
- `/privacy/`, `/terms/` — описание обработки данных и статуса ресурса.
- `assets/css/conversion.css` — новый дизайн; собирается с базовыми стилями через Hugo Pipes.
- `data/eligibility.yaml` — форматы, источник, статус и дата проверки. Без подтверждённой матрицы проверка всегда направляет в официальную анкету, не обещая допуск.
- Sveltia CMS: коллекции «Рекламные лендинги» и «Условия подключения».

Подробности реализации и проверки перед рекламой: [отчёт](work/site-improvement-2026-11-21.md).

## Проверки

```bash
node --test scripts/test-conversion.mjs
hugo --minify --destination /tmp/kurergo-check
python3 scripts/check-built-site.py /tmp/kurergo-check
```

Проверка сборки сравнивает сохранённые в Git HTML-пути из `public/`, ссылки, каноникал, JSON-LD, sitemap и партнёрский URL. Файлы `public/` вручную не правятся: деплой пересобирает их из исходников.

## Локальный запуск

```bash
hugo server -D
```

## Сборка

```bash
hugo --gc --minify
```

## GitHub Pages

Workflow находится в `.github/workflows/hugo.yml`. После push в ветку `main` GitHub Actions установит Hugo, соберет сайт и опубликует его в GitHub Pages.

## Блог

Статьи лежат в `content/wiki/`. Для новой статьи можно создать Markdown-файл с front matter:

```md
---
title: "Название статьи"
date: 2026-06-02
description: "SEO-описание"
keywords: ["ключ", "ключевая фраза"]
---
```

## Редактирование контента

Сохраняйте существующие `slug`, `url` и `aliases`, если задача не предполагает миграцию адресов. При содержательной правке обновляйте `lastmod`; дата публикации остаётся прежней. Для FAQ используйте поле `faq` во front matter: общий шаблон выводит и видимые ответы, и JSON-LD. Не дублируйте эти ответы вручную в конце Markdown.

Начинайте материал с ответа на конкретный вопрос. Добавляйте подходящие к теме инструкции, расчёты и источники. Примеры с числами явно обозначайте как условные; не выдавайте их за тарифы или статистику. В городских материалах не публикуйте неподтверждённые обещания спроса, дохода и доступности подключения.

Скрипты `generate-*-seo-articles.mjs` и `expand-short-blog-articles.mjs` содержат старые шаблоны. Их повторный запуск может перезаписать редактуру и вернуть массовые повторы; не используйте их для обновления существующих статей без отдельной переработки генераторов и проверки diff.
